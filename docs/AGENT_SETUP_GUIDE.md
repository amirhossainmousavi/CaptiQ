# CaptiQ — راهنمای پیش‌نیاز برای ایجنت (قبل از شروع پیاده‌سازی)

این فایل مکمل `PROJECT_SPEC.md` است و ابهاماتی که در اسپک اصلی وجود داشت را با تصمیم‌های مشخص پر می‌کند. این فایل را **همراه با** PROJECT_SPEC.md به ایجنت بدهید.

> **به‌روزرسانی مهم (نسخه‌ی ۲):** معماری BYOK (بخش ۰ نسخه‌ی قبلی) **لغو شد**. تصمیم نهایی: پروژه به‌صورت متن‌باز منتشر می‌شود و هر کسی که آن را دیپلوی می‌کند، API key و provider/model انتخابی خودش را در فایل `.env` سرور قرار می‌دهد (نه در body هر request). ورودی API عمومی فقط `videoUrl` است. جزئیات در بخش ۰ جدید زیر آمده است.

---

## ۰. معماری نهایی: کلید و Provider ثابت در `.env` (نسخه‌ی متن‌باز)

### ۰.۱ Endpoint

```
POST /api/subtitles
Content-Type: application/json

{
  "videoUrl": "https://www.youtube.com/watch?v=dQw4w9WgXcQ"
}
```

فقط همین یک فیلد. هیچ `apiKey`، `provider`، یا `model`ی در body نیست — همه‌ی این‌ها از `.env` خونده می‌شن.

### ۰.۲ `.env` — تنظیم provider و کلید فعال

```env
# کدوم provider فعاله (یکی از: openai, google, openrouter)
AI_PROVIDER=openai

# کلید مربوط به همون provider فعال
AI_API_KEY=

# مدل انتخابی (بسته به provider فرق می‌کنه، مثلاً gpt-4o-mini یا gemini-flash-latest)
AI_MODEL=gpt-4o-mini
```

- سرور در زمان start-up فقط provider مشخص‌شده در `AI_PROVIDER` رو مقداردهی می‌کنه (طبق همون `LLMProvider` interface که قبلاً ساختیم — این معماری هنوز مفیده چون کاربران دیگه‌ی این پروژه‌ی متن‌باز ممکنه provider دیگه‌ای بخوان).
- اگه `AI_API_KEY` خالی باشه یا `AI_PROVIDER` مقدار نامعتبر داشته باشه، سرور باید در همون startup خطای واضح بده و بالا نیاد (نه این‌که موقع request fail کنه).
- دیگه نیازی به validation کلید/provider در body request نیست چون از env میان؛ Zod schema باید فقط `videoUrl` رو چک کنه.

### ۰.۳ ملاحظات امنیتی (تغییر کرده)

- چون کلید حالا مال صاحب دیپلویمنته (نه end-user)، دیگه نگرانی «کلید کاربر لو نره در response» به همون اندازه‌ی قبل حیاتی نیست، ولی همچنان:
  - `AI_API_KEY` هرگز نباید در لاگ چاپ بشه.
  - `.env` باید در `.gitignore` باشه (چون پروژه متن‌بازه، این خیلی مهمه — یه نمونه `.env.example` بدون مقدار واقعی باید در ریپو باشه).
- HTTPS همچنان برای production توصیه می‌شه ولی دیگه به‌خاطر یک الزام امنیتی حیاتی (مثل انتقال کلید کاربر) نیست.

## ۱. الگوریتم دقیق انتخاب زیرنویس (Tie-breaking)

ترتیب دقیق چک کردن باید این باشد (ایجنت باید همین ترتیب را پیاده کند، نه انتخاب آزاد):

```
1. en (manual)
2. en-US (manual)
3. en-GB (manual)
4. هر واریانت دیگر en-* (manual)
5. en (auto-generated)
6. en-US (auto-generated)
7. en-GB (auto-generated)
8. هر واریانت دیگر en-* (auto-generated)
```

اولین موردی که پیدا شد انتخاب و پردازش متوقف می‌شود. اگر هیچ‌کدام پیدا نشد، خروجی خطای استاندارد (طبق اسپک اصلی) برگردانده شود.

---

## ۲. مدیریت خطای yt-dlp و Rate Limit

- **Retry policy**: حداکثر ۲ بار تلاش مجدد با فاصله‌ی نمایی (exponential backoff: مثلاً ۱ ثانیه، سپس ۳ ثانیه).
- اگر یوتیوب کپچا/بلاک برگرداند، retry نکن (بی‌فایده است) و فوراً خطای مشخص برگردان: `"error": "YouTube rate-limited the request, try again later"`.
- **Timeout** برای هر عملیات yt-dlp: ۳۰ ثانیه. اگر رد شد، عملیات را kill کن و خطای timeout برگردان.
- فعلاً استفاده از proxy یا rotation ضروری نیست؛ این را به فاز بعدی (Phase 6 آینده) موکول کنید.

---

## ۳. استراتژی Chunking برای ترجمه‌ی AI

زیرنویس‌های طولانی (ویدیوهای بلند) نباید یکجا به AI ارسال شوند.

- هر batch حداکثر **۵۰ خط زیرنویس** یا **۳۰۰۰ کاراکتر متن** (هرکدام زودتر پر شد).
- batchها به‌صورت **ترتیبی** (نه موازی) پردازش شوند تا از rate limit مدل AI جلوگیری شود؛ اگر بعداً performance مهم شد، می‌توان به pool محدود (مثلاً ۳ درخواست همزمان) تغییر داد.
- خروجی هر batch باید validate شود (JSON معتبر و تعداد خط‌های ورودی/خروجی برابر باشد)؛ در صورت mismatch، همان batch یک‌بار دیگر retry شود، در صورت شکست مجدد، متن اصلی (بدون ترجمه) برای آن بخش برگردانده شود به همراه فلگ `"partialTranslation": true`.

---

## ۴. Concurrency و صف‌بندی درخواست‌ها

- فعلاً نیازی به صف پیچیده (مثل BullMQ) نیست.
- اما باید یک **in-memory lock به ازای هر videoId** وجود داشته باشد: اگر درخواست دومی برای همان videoId قبل از اتمام اولی برسد، منتظر نتیجه‌ی همان پردازش بماند (به‌جای اجرای دوباره‌ی extraction).
- این را می‌توان با یک `Map<videoId, Promise>` ساده در `cache.service.ts` پیاده کرد.

## ۵. فایل `.env.example` (باید از همون اول ساخته شود)

```env
PORT=3000
NODE_ENV=development

# AI Provider — کدوم provider فعاله و کلید/مدل مربوط به همون
AI_PROVIDER=openai
AI_API_KEY=
AI_MODEL=gpt-4o-mini

# yt-dlp
YT_DLP_PATH=yt-dlp
YT_DLP_TIMEOUT_MS=30000

# Cache
CACHE_DIR=./cache
CACHE_TTL_HOURS=168

# CORS
ALLOWED_ORIGIN=chrome-extension://YOUR_EXTENSION_ID
```

> این نسخه‌ی نهایی env است (طبق معماری بخش ۰). کلید و provider دیگر در request نمی‌آیند.

## ۶. نسخه‌ها و Package Manager (باید صریح مشخص شود)

- Node.js: **نسخه‌ی ۲۰ LTS یا بالاتر**
- Package manager: **npm** (مگر ترجیح دیگری دارید)
- TypeScript: **strict mode فعال** (`"strict": true` در tsconfig)
- حتماً یک فایل `.nvmrc` با محتوای `20` اضافه شود تا نسخه‌ی Node قفل شود.

---

## ۷. CORS

- فقط origin اکستنشن کروم مجاز باشد (`chrome-extension://<id>`)، نه `*`.
- تا زمانی که ID نهایی اکستنشن مشخص نشده، از `ALLOWED_ORIGIN` در `.env` بخوان (بالا تعریف شد) تا سخت‌کد نشود.

---

## ۸. لاگینگ

- فرمت لاگ: **JSON ساختاریافته** (نه متن ساده) تا بعداً قابل parse باشد.
- سطوح لازم: `info`, `warn`, `error`.
- حداقل این رویدادها باید لاگ شوند: شروع/پایان extraction، cache hit/miss، خطای yt-dlp، خطای AI، زمان کل پردازش هر درخواست (برای دیباگ کندی‌ها).
- **هرگز API key کاربر یا محتوای کامل زیرنویس را در لاگ ننویس** (فقط videoId، provider/model انتخابی، و طول زیرنویس کافیست). این نکته با معماری BYOK اهمیت بیشتری پیدا کرده چون کلید متعلق به کاربر است، نه سرور.

---

## ۹. مدیریت Cache

با معماری نهایی (provider/model ثابت در `.env`)، کش می‌تواند ساده‌تر شود، اما بهتر است همچنان provider/model در کلید لحاظ شود تا اگر بعداً `.env` عوض شد، کش قدیمی با مدل جدید قاطی نشود:

- **کش زیرنویس اصلی (بدون ترجمه)**: `videoId_language`، مستقل از provider. مثال: `cache/original/dQw4w9WgXcQ_en.json`
- **کش ترجمه‌شده**: `videoId_language_provider_model` (provider/model از env خونده می‌شه، نه از request). مثال: `cache/translated/dQw4w9WgXcQ_en_openai_gpt-4o-mini.json`
- **TTL**: هر ورودی کش بعد از ۷ روز منقضی شود (`CACHE_TTL_HOURS` در env).
- یک mechanism ساده cleanup لازم است: هنگام هر request جدید، فایل‌های منقضی‌شده در پس‌زمینه پاک شوند (نیازی به cron جداگانه در فاز اول نیست).

---

## ۱۰. استراتژی تست (فاز اول)

- تست خودکار (Jest) لازم نیست در فاز اول؛ اما ایجنت باید بعد از هر فاز، تست دستی با ۲-۳ videoId واقعی زیر انجام دهد و خروجی را نشان دهد:
  - یک ویدیوی با زیرنویس دستی انگلیسی (مثلاً یک سخنرانی TED)
  - یک ویدیوی با فقط auto-generated caption
  - یک ویدیوی بدون زیرنویس انگلیسی (برای تست مسیر خطا)
- بعد از فاز ۲ به بعد، حتماً باید Jest اضافه شود برای تست واحد `subtitle.parser.ts` (تبدیل VTT/SRT به JSON) چون این بخش پرخطاترین قسمت پروژه است.

---

## ۱۱. نکته‌ی حقوقی (تصمیم خودتان است، نه ایجنت)

استفاده از yt-dlp برای دانلود محتوای یوتیوب ممکن است با شرایط استفاده‌ی یوتیوب (ToS) در تضاد باشد. این پروژه فقط زیرنویس (نه ویدیو) استخراج می‌کند که ریسک کمتری دارد، اما بهتر است قبل از انتشار عمومی این را با یک مشاور حقوقی یا حداقل با مطالعه‌ی دقیق ToS بررسی کنید. این تصمیم را از ایجنت هوش مصنوعی نخواهید.

## ۱۲. فایل AGENT_RULES.md (پیشنهادی، جدا از اسپک محصول)

این قوانین را به‌عنوان یک فایل جدا (نه بخشی از PROJECT_SPEC) به ایجنت بدهید تا بین "چی بساز" و "چطور بساز" تفکیک باشد:

```markdown
# Agent Rules

- هرگز API key یا secret را hardcode نکن؛ همیشه از process.env استفاده کن.
- API key کاربر (که در body هر request می‌آید) هرگز نباید cache، لاگ، یا در پیام خطا echo شود؛ فقط در حافظه‌ی همان request زندگی می‌کند.
- در هر تابع async حتماً try/catch داشته باش و خطا را با فرمت JSON استاندارد پروژه برگردان.
- بعد از اتمام هر فاز (Phase 1 تا 5)، خلاصه‌ای از تغییرات + نتیجه‌ی تست دستی را گزارش بده، قبل از رفتن به فاز بعد.
- کد را با ESLint + Prettier فرمت‌بندی کن (config پیش‌فرض قابل قبول است مگر خلاف آن گفته شود).
- هیچ dependency جدیدی بدون ذکر دلیل اضافه نکن.
- کد بدون کامنت نوشته شود؛ اسم متغیرها/توابع باید به‌قدری واضح باشند که نیاز به توضیح اضافه نداشته باشند (خوانایی از طریق نام‌گذاری، نه کامنت).
- استثنا: اگر یک تصمیم غیربدیهی یا workaround فنی وجود دارد که بدون توضیح قابل فهم نیست، فقط همان یک خط توضیح مجاز است.
- قبل از تغییر ساختار پوشه‌بندی تعریف‌شده در اسپک، تایید بگیر.
```
